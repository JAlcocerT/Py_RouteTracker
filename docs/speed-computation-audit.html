Correction: Finding 1's original root cause was backwards

Corrected · 2026-08-13

Finding 1 and its Evidence section below (kept as originally published, for the reasoning trail) concluded the GoPro path's m/s → km/h, ×3.6 conversion was correct, and that the double-conversion risk was a narrow edge case limited to non-GoPro-native dumps carrying an explicit unit suffix. That conclusion was wrong, and the "evidence" for it was circular: it only checked that raw × 3.6 looked like a plausible speed, never independently confirming the real speed with the person who recorded it.

Testing against a real HERO13 Black clip surfaced the actual mechanism: ExifTool's own GoPro.pm module already converts GPMF's raw m/s speed to km/h before it ever prints the GPS Speed line — both its GPS5 (Hero5/6/9) and GPS9 (Hero11+) tag tables define the tag identically: 

3 => {
    Name => 'GPSSpeed',
    Notes => 'stored as m/s but converted to km/h when extracted',
    ValueConv => '$val * 3.6',
},

(exiftool/exiftool, lib/Image/ExifTool/GoPro.pm)

So a bare, unit-less GPS Speed number — the normal case for genuine GoPro footage, not a rare exception — is always already in km/h. The original code's unconditional × 3.6 was therefore a straightforward, universal double-conversion affecting essentially every GoPro upload, not the narrow unit-suffix corner case described below. The fix now treats a bare number as already-km/h (factor 1.0) and only multiplies by 3.6 when a line is explicitly labeled m/s.

This was confirmed two ways on the real HERO13 clip: (1) a fix's reported speed jumped from 0 to 86.19 within 0.1s of GPS lock reacquiring — physically impossible as an m/s reading (880g of acceleration) but an ordinary speed as km/h; (2) the literal ExifTool source above, not a paraphrase of it.

All four findings below have been fixed

Resolved · 2026-08-12, corrected 2026-08-13

This report is kept as-written for the reasoning trail; the fixes themselves live in the code. Summary of what changed, same numbering as below:

  1. Finding 1 (see correction above) — gopro_embedded.py's speed parser now treats a bare GPS Speed number as already-km/h (ExifTool's own GoPro.pm already applies that conversion) instead of re-multiplying it by 3.6, while still honoring an explicit unit suffix (convert_speed_to_kmh) for non-native dumps.

  2. Finding 2 — smooth_speed_outliers now accepts each sample's real timestamp and sizes its window from the actual sample rate (targeting ~0.5s of coverage) instead of a flat 5-sample window; both telemetry sources pass their timestamps through.

  3. Finding 3 — parse_gps_data now places each fix within its own GPMF block's real video-time span (read from that block's Sample Time) instead of spreading every fix evenly across the whole video.

  4. Finding 4 — video upload now defaults target_fps to the footage's own frame rate (get_video_fps, via ffprobe) instead of a flat constant, when the caller doesn't override it.

Summary

Read this alongside the correction banner above — the paragraph below is kept as originally written. The GPX path's haversine-distance-over-time speed is correct, verified against the repo's own bundled fixture (see Evidence below). The GoPro path's m/s → km/h conversion was originally believed correct too, on the strength of evidence that turned out to be circular; it was actually being applied twice. A prior bug that let single isolated GPS glitches read as ~300 km/h is fixed and covered by test_speed_smoothing.py, though a longer GPS lock-loss burst can still slip through it — see the new finding below.

What's not covered is anything that biases every sample the same way, or a genuine (not glitched) reading that just lands at the wrong moment. Two things in the pipeline can do exactly that, and both would present to a user as "the speed looks unrealistically high" without ever tripping the existing spike filter. Finding 1 is the one most likely to explain a consistently inflated readout; Finding 2 explains occasional spikes that survive the existing smoothing. A short diagnostic checklist at the end tells you which one you're looking at.

Findings

The GoPro parser trusts a number it never actually checks the units of

Priority 1 · High

backend/app/telemetry/sources/gopro_embedded.py:33,83 pulls the speed value out of the raw exiftool -ee text dump with this regex, then unconditionally treats the result as metres/second: 

_SPEED_RE = re.compile(r"GPS Speed\s+:\s+([\d.]+)")
...
data.append({"speed": float(m_spd.group(1)) * 3.6, "lat": cur_lat, "lon": cur_lon})

[\d.]+ stops at the first character that isn't a digit or a dot. If the source line ever looks like GPS Speed : 42.0 km/h instead of the unit-less GPS Speed : 0.208 this app's own GoPro fixture produces — which is exactly how ExifTool prints the standard EXIF/QuickTime GPSSpeed tag when a GPSSpeedRef of K/M/N is present, as opposed to GoPro's own unit-less GPMF GPS5 stream — the regex silently keeps just the leading digits and discards the unit. The already-km/h number then gets multiplied by 3.6 again, inflating every reading by roughly the same factor for the rest of the session (about 3.6× for a km/h source, about 1.6× for mph).

This is the specific reason it's worth flagging on its own, separate from "add more validation": smooth_speed_outliers (resample.py:14) is a Hampel filter — it flags a sample by comparing it to its local neighbors. A uniform multiplicative bias moves every neighbor by the same factor, so nothing ever looks locally anomalous and the filter has no way to catch it. It was built to catch spikes, not scale errors, and a scale error is the shape of bug that produces a speedometer that's wrong all the time rather than wrong for a frame or two.

Suggested fix

Don't drop the text after the number — check for a trailing unit token (km/h/mph/kn/none) and convert based on what's actually there instead of assuming m/s. As a second, independent safety net: this file already has lat/lon for every fix, so a haversine cross-check (the same math external_gpx.py already does) between consecutive points can sanity-check the device-reported speed on ingestion. If the ratio between the two doesn't cluster near 1.0 across the session, that's a unit mismatch, and it's cheap to detect right where the data comes in rather than downstream where it just looks like "an unrealistic number."

The outlier filter's window doesn't scale with the real GPS sample rate

Priority 2 · Medium

smooth_speed_outliers(speed, window=5, ...) is called with the same fixed window=5 from both gopro_embedded.py:103 and external_gpx.py:67, regardless of how fast the underlying source actually samples. I measured the real rate in the repo's own GoPro fixture (see Evidence): about 18–19 GPS fixes per second, matching the module's own docstring. At that rate a 5-sample window only outvotes a dropout up to roughly 2–3 consecutive bad fixes — about 110–170 ms — before the bad samples start dominating their own window and surviving the filter untouched.

A real GPS signal loss (going under a bridge, through a stand of trees, along a building-lined street) routinely lasts longer than that — several hundred milliseconds to a couple of seconds is normal, not exotic. When it does, the resulting bad fix isn't a single-sample glitch anymore, it's a short run that reads as a genuine local maximum to the filter and passes straight through onto the speedometer for however many frames it spans. This is functioning exactly as documented (the module's own docstring already admits "a dropout lasting more than about half the window can't be distinguished from a real sustained speed change") — it's a real, load-bearing limitation, not a defect in the filter's logic, but it's the second most likely explanation for "unrealistically high" if what's actually being seen is a brief spike rather than a sustained inflation.

Suggested fix

Size the window from the source's actual sample rate rather than a flat constant — e.g. derive it from the median time delta between fixes so it always covers a fixed duration (~0.5s is a reasonable start) instead of a fixed sample count. That also fixes the inconsistency where the same window=5 is simultaneously tight for GoPro's ~18 Hz and comparatively loose for a 1 Hz phone/Garmin GPX track.

GoPro sample timing is approximated, not read from the stream

Priority 3 · Info

gopro_embedded.py:102 assigns every parsed GPS fix a time via np.linspace(0, duration_sec, len(df)) — i.e. it assumes fixes are spaced perfectly evenly across the entire video. The raw exiftool dump actually carries real per-block anchors (Sample Time/Sample Duration once per ~1s GPMF block, and a real-world GPS Date Time alongside it) that this parser reads past without using. In the bundled fixture the assumption holds up well because the fix rate is fairly steady throughout, but on a session with an uneven GPS lock (weak signal at the start, a pause, a tunnel) the linspace approximation will place a correct speed reading at a slightly wrong moment in the video. On its own that's a sync/precision issue rather than a magnitude one — but paired with Finding 2, a misplaced reading is exactly what turns "the car briefly lost GPS lock under that bridge" into "the HUD said 90 km/h while I was clearly stopped at the light."

HUD frame rate is fixed at 30fps, independent of the source footage

Priority 4 · Info

Telemetry is resampled onto a grid at target_fps (core/config.py:16, default 30, user-configurable at upload) regardless of the actual video's frame rate. overlay_png_sequence (core/ffmpeg_utils.py:61) then composites that fixed-rate HUD PNG sequence onto the trimmed footage at its own native rate. For 30fps footage this lines up by construction; for anything that isn't — 60fps or variable-frame-rate action-cam clips are common — the HUD (and the speed number it's showing) can drift out of sync with the real footage over a long clip, which reads as "wrong speed for what's on screen" even though the underlying number was correct for its own timestamp.

A real GPS lock-loss burst isn't fully caught by outlier smoothing

New · Open, not yet fixed · 2026-08-13

Found while validating the Finding 1 correction against a real 14-minute HERO13 clip. Around a specific ~2-second span, GPSDOP jumps from a healthy 5.15 to 33.5-99.99 (poor/no-fix) for roughly 25 consecutive samples, and GPS Altitude swings wildly in lockstep (364m → -247m → 189m) — a textbook GPS lock-loss/reacquisition glitch, not a units problem. The GPS Speed field glitches the same way, up to 958.96 (already km/h, post-Finding-1-fix) for that stretch.

smooth_speed_outliers's adaptive Hampel window (Finding 2's fix) targets ~0.5s of coverage — for this camera's ~10 Hz native rate that's roughly 5 samples, well short of the ~25-sample burst here. A rolling-median filter can't out-vote an outlier run that's longer than about half its own window, so this burst survives smoothing intact: running the current (fixed) pipeline against this real clip still produces a max reading of 936 km/h for that span, even though the median for the rest of the session is a believable ~53 km/h.

Suggested fix

GPSDOP (GPS9) / GPS Horizontal Positioning Error (GPS5) is a direct, reliable fix-quality signal already present in the dump — filtering out fixes above a DOP threshold (e.g. >10) before interpolation/smoothing would remove this class of burst at the source, rather than trying to statistically out-vote it after the fact. Not implemented yet — flagging for a decision on whether to address it now.

Diagnostic checklist

Four quick checks to tell which finding actually applies to your footage:

  1. Open the raw dump.

    Find <video-stem>_exiftool.txt in the backend's telemetry cache directory and look at a GPS Speed line. A bare number (GPS Speed : 12.500) is the expected GoPro GPMF shape and is already km/h (see the correction above) — no further scaling needed. A number with a unit attached (12.500 km/h or mph) means a different/non-native tool wrote this dump; convert using that unit instead.

  2. Sustained or brief?

    If the number is unrealistic for the whole session (or the whole session scaled up by a consistent-feeling factor), that's Finding 1. If it's fine most of the time and jumps for a second or two at specific moments, that's Finding 2.

  3. Do the jumps line up with real GPS-hostile spots?

    Bridges, tunnels, dense tree cover, tall buildings. If the brief spikes cluster there, that confirms Finding 2 rather than a random glitch.

  4. Check the ratio.

    Divide the displayed peak by a known-plausible real top speed for that session. A result near 3.6 pointed at exactly this bug — an already-km/h GoPro reading getting re-multiplied by 3.6 (now fixed). Anything else is more likely the outlier-burst issue below than a unit bug.
